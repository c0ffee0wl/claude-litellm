# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

claude-litellm is a Linux-side setup repo that installs and configures the [LiteLLM Proxy](https://docs.litellm.ai/) AI gateway as a systemd user service on `127.0.0.1:4000`, plus optionally Claude Code with managed settings. LiteLLM speaks Anthropic's Messages format natively on `/v1/messages` and translates to Azure / Vertex Gemini / etc. via `model_list` entries.

There is no build system, test suite, or linter — this is a deployment automation repo of Bash scripts plus YAML/JSON configs.

## Architecture

Single execution context: Linux. Runs as the current `$USER` (no devuser, no sudo for the script itself; `sudo` is invoked only for `apt`, `loginctl enable-linger`, and writing `/etc/claude-code/managed-settings.json`).

Entry point: `linux/setup.sh`. It sources `linux/common.sh` for utilities and runs phases 0–11. Key flags (`--router-only`/`--harden-only`/`--install-only` mutually exclusive; `--install-obsidian`, `--docker`, and `--no-profile-toggles` additive — except `--docker` + `--harden-only`/`--install-only`, rejected since neither installs LiteLLM; not persisted across reruns; a deprecated `--yes` is accepted as a warned no-op so external callers that still pass it — e.g. ct-dfir-llm — keep working):
- `--router-only` skips Phase 8a (system-level managed-settings.json sudo-install) and Phase 8e (nah Claude Code plugin — also a policy layer); Phase 8b (`/tmp/claude` sandbox prereq, no sudo) now runs in **all** modes so the router-only `/sandbox` opt-in isn't missing its prereq dir. User-level Phase 8c–8d (`~/.claude/settings.json` statusLine, `~/.claude/statusline.sh`) still run, but Phase 8c keeps the full `sandbox` block and sets `enabled:false` (`jq '.sandbox.enabled = false'`, **not** stripped) so router-only ships the sandbox **off** by default with the credential/network floor pre-configured — flip `enabled:true` to turn it on. The bwrap runtime is installed in all modes (Phase 2). Router-only also skips `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (Phase 5a, removed if present) so a dev box keeps the full subprocess env (incl. the gateway token) for Bash/MCP/hooks. LiteLLM + Claude Code + claude-devtools all install locally — useful for a dev box where you want to route through LiteLLM without system-level policy enforcement.
- `--harden-only` is the inverse: skips Phases 4a (LiteLLM), Phase 5b (provider-secret collection), Phase 6 (Postgres + LiteLLM env file), Phase 7 (`litellm.service`), and Phase 9 (`claude-devtools.service`). Phase 5a's `~/.profile` writes still run; Phase 10's cleanup-only uninstaller for the legacy claude-run / claude-history service runs in every mode. Installs only Claude Code + managed-settings — useful when LiteLLM runs on another host. To point at a remote router, set `ANTHROPIC_GATEWAY_URL=http://<remote>:4000` in `.env` before running — `set -a` sourcing lets `.env` override the localhost default, which then lands in `~/.profile` as `ANTHROPIC_BASE_URL`. Note the deployed statusline classifies a remote router as DIRECT mode (its LITELLM mode matches loopback `:4000` only), so line 2 shows model + context but no upstream-model/spend suffix.
- `--install-only` is the third standalone mode (mutually exclusive with `--router-only`/`--harden-only`, and rejected with `--docker` since it installs no LiteLLM). It combines the LiteLLM/Postgres skips of `--harden-only` (Phases 4a, 5b, 6, 7) with the policy skips of `--router-only` (Phase 8a managed-settings + 8e nah; Phase 8c ships the `sandbox` block `enabled:false`; Phase 5a `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` removed), and on top of both **skips all Phase 5a gateway wiring**: no `sk-` master key is minted, and `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`/`LITELLM_API_KEY`/the `ANTHROPIC_DEFAULT_*_MODEL` selectors + `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY`/`CLAUDE_CODE_ALWAYS_ENABLE_EFFORT` are **not** written to `~/.profile` (the latter two are removed if present, so a box flipped from a gateway mode is cleaned up). The telemetry/privacy/feature toggles + `NO_PROXY`/`API_TIMEOUT_MS` still land in `~/.profile`. Phase 4b (Claude Code) and **Phase 9 (claude-devtools, RAM-gated)** still install — the difference from `--harden-only` is that devtools comes along and no managed-settings/nah/gateway wiring is applied. Net: a configured, hardened Claude Code install that hits the real Anthropic API until the user sets `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` themselves to point at a router. `NEEDS_MODEL_CONFIG` stays 0 (its banner never fires); the end-of-script banner prints an install-only note instead of the LiteLLM UI/credentials.
- `--install-obsidian` is additive (combinable with any mode, not part of the mutual-exclusivity check): it enables Phase 4c (ACP adapter via `bun add -g`) and Phase 4d (latest Obsidian amd64 `.deb`). ACP is **only** installed with this flag — it is no longer a full-mode default. The ACP bridge exists to drive Claude Code from editors like Obsidian, so the two are paired behind one flag.
- `--no-profile-toggles` is additive (combinable with any mode): Phase 5a's Claude Code toggle writes to `~/.profile` — the managed env-block mirror loop (which since 2026-08-08 also carries `DISABLE_GROWTHBOOK` + `CLAUDE_CODE_ATTRIBUTION_HEADER` in the `env:` block) plus the explicit `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`/`CLAUDE_CODE_FORK_SUBAGENT` UX prefs — flip to `remove_profile_export`: nothing is written and previously-written toggles are **scrubbed**, so already-deployed boxes self-heal on their next run. For overlays (ct-dfir-llm/ct-kali-llm) whose own setup deploys `/etc/claude-code/managed-settings.json` carrying these entries in its `env:` block — the mirror's job is covering boxes where no managed env: block delivers the toggles, so an overlay that ships its own opts out of the redundant copy. Everything else in Phase 5a (gateway URL/master key, shell-wide telemetry opt-outs, model selectors, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` handling) is unaffected. Caveat for overlay authors: with the mirror off, a toggle added to this repo's `env:` block no longer reaches the overlay's boxes — it must be mirrored into the overlay's own managed-settings `env:` block. Note the flag also flips the two UX prefs from user-unsettable-profile to (on the overlay side) enforced managed env — the overlays chose that trade deliberately.
- `--docker` is additive (combinable with any mode except `--harden-only`/`--install-only`, which install no LiteLLM): it runs **LiteLLM** as a rootless Docker Compose service instead of the native uv install. Enables Phase 2b (`install_docker_rootless` in `common.sh`), skips Phase 4a (uv litellm + `prisma generate` — the image bundles both), and makes Phase 7 deploy `litellm-docker-compose.yml` + the `litellm-docker.service` unit (`docker compose up`) under the canonical `litellm` user-service name. **Only LiteLLM is containerized** — Postgres stays on the host (so `/ui` models/keys/spend persist across the native↔docker switch — no fresh DB volume) and **claude-devtools stays native** (Phase 9; its vite build OOMs the same in `docker build`, and the image isn't built on-host anyway). Rootless is deliberate (no root daemon, no `docker` group ≈ root) — see *Docker mode (`--docker`)* below.

API keys come from `.env` in the repo root (gitignored; create from `.env.example`) — or from any provider env var you happen to have exported in your shell / `~/.profile`. `.env` is optional: if it's missing, Phase 5 logs a warning and continues, picking up whatever is already exported. `setup.sh` Phase 5 auto-discovers them via `collect_litellm_provider_vars` in `common.sh` (pattern `*_API_{KEY,BASE,VERSION,TOKEN}` plus a named list for AWS/GCP/watsonx/Azure-AD/OpenAI-org/HF extras) and writes the matches plus the LiteLLM master key + DB URL **only** to `~/.config/litellm/env` (the systemd EnvironmentFile, mode 600). The user's `~/.profile` gets only the gateway URL, the master key as `ANTHROPIC_AUTH_TOKEN`, and telemetry opt-outs — no upstream provider secrets.

LiteLLM speaks Anthropic on `/v1/messages` (the unified endpoint, not the `/anthropic/*` pass-through). Claude Code is configured via `ANTHROPIC_BASE_URL=http://127.0.0.1:4000` (no path suffix).

## Setup Phases (`linux/setup.sh`)

| Phase | What |
|---|---|
| 0 | self-update: `git pull --ff-only` and re-exec if behind. The **whole run** exits early (exit 0) while `claude`/ACP is running — deliberate, to avoid replacing binaries or restarting the proxy mid-session; when not a git checkout, only the self-update is skipped. |
| 1 | shell profile setup: ensure `~/.profile` and the `~/.bash_profile` shim sourcing it exist |
| 2 | apt: `git curl jq ca-certificates unzip rsync` + `bubblewrap socat ripgrep` (all modes, + `configure_bwrap_apparmor`). The `apt-get update` + install round-trip is skipped when every package already reports `install ok installed`; apt installs go through `apt_install`/`apt_update_once` (common.sh) — the index is refreshed at most once per run (2b re-runs the update itself after adding the Docker repo, then re-marks it fresh) and `APT_CHANGED` feeds Phase 11's autoremove. The sandbox runtime ships everywhere so a user can opt into `/sandbox` via the UI even under `--router-only` (which ships the sandbox **off** by default — Phase 8c sets `enabled:false` but keeps the block, and the runtime stays installed). The packages are tiny + benign. `ripgrep` is an undocumented `/sandbox` dependency — the Mode/Overrides toggle tabs only render once it resolves (anthropics/claude-code#31804, #31708); a real `rg` binary keeps the sandbox toggle reachable |
| 2b | (only with `--docker`) `install_docker_rootless` (common.sh): install Docker CE from the official apt repo (GPG key + `download.docker.com` sources, Kali→trixie fallback — apt-repo block reused near-verbatim from `/opt/linux-setup`), then set it up **rootless** (`dockerd-rootless-setuptool.sh install` → `systemd --user` `docker.service`; **no** `docker` group). If a rootful daemon is already running (writable `/var/run/docker.sock`), the setuptool is invoked with `--force` so rootless coexists alongside it on a separate per-user socket (forced only when that socket is present, so a clean box keeps the setuptool's RootlessKit smoke-test fatal). Installs `docker-ce{,-cli} containerd.io docker-{buildx,compose}-plugin docker-ce-rootless-extras uidmap slirp4netns dbus-user-session`. Idempotent (skips the **engine** install if `docker` present but still ensures the rootless + compose deps `uidmap slirp4netns dbus-user-session docker-ce-rootless-extras docker-compose-plugin` via a `dpkg -s` check — a pre-existing engine commonly lacks `uidmap` (setuptool aborts "Missing system requirements … apt-get install -y uidmap") or, on a `docker.io` host, the `docker compose` plugin the litellm unit's `docker compose up`/`down` need; skips setuptool if `~/.config/systemd/user/docker.service` exists) |
| 3 | bun + uv: install if missing, else upgrade in place (`bun upgrade`, `uv self update` — the latter skipped cleanly for non-standalone installs); symlink `node→bun`; `npx` is a small wrapper script exec'ing `bun x` (a plain symlink fails — bun's argv[0] sniffing only recognises `bunx`/`node`) |
| 4a | LiteLLM via `uv tool install --with prisma --with 'fastapi<0.140.7' 'litellm[proxy,proxy-runtime]>=1.84.0'` → `~/.local/bin/litellm`; an existing install is upgraded in place (`--upgrade`, re-asserting the floor), with the litellm unit **stopped and runtime-masked across the whole phase** (see the stop-window paragraph under Troubleshooting for the mechanism), and the Prisma toolchain is healed + warmed on every pass (nodeenv + CLI-cache heals and a bounded `prisma --version`) before the Prisma client is generated (force-regenerated on a real version change or when `from prisma import Prisma` fails the import probe — LiteLLM syncs the schema at startup via `prisma db push` (see *DB schema posture* under Key Conventions) and crashes without a generated client). On a cold box, generate downloads query engines for **all five** `binaryTargets` litellm's schema lists for its Docker images (~75MB compressed → ~138MB on disk) even though a native box only ever executes the computed one — verified unavoidable at prisma 5.17: `PRISMA_CLI_BINARY_TARGETS` looks like the lever but is read only by `@prisma/engines`' npm postinstall (`ensureBinariesExist` in its dist source), never by generate's per-schema downloads (tested cold 2026-08-20 — the env var provably reached the CLI, 138MB still fetched), **so do not re-try it**. Bounded impact: once per engine hash per box — `~/.cache/prisma` and the `node_modules` engine copies persist across litellm upgrades, and the heals never remove them (the generated client also resolves `BINARY_PATHS` by executability — first engine whose `--version` runs wins, prisma 0.15.0 `engine/utils.py` — so the extra engines are dead weight, not a correctness need). The warm-up and generate steps log their durations, so a slow run attributes itself from the log. Every Prisma CLI call goes through the `run_prisma` wrapper, which sources `~/.config/litellm/prisma.env` (rendered by Phase 4a from `linux/configs/litellm-prisma.env`; the **single source** of the Prisma switches for the wrapper *and* the unit's `EnvironmentFile=`, so what setup.sh warms is structurally what the service reads: the flat `PRISMA_BINARY_CACHE_DIR`, `PRISMA_USE_GLOBAL_NODE=false` — never probe an ambient `node`; on these boxes that is the Phase 3 `~/.bun/bin/node → bun` symlink, and bun ≥1.4.0 answers the library's `node --version` probe with a REPL that waits on a TTY forever, the 2026-08-22 stall, see Troubleshooting — `CHECKPOINT_DISABLE=1` (Prisma CLI phone-home), the npm cooldown, and the `LITELLM_PRISMA_*` budgets; a change to it restarts the service via `LITELLM_CHANGED`), redirects stdin from `/dev/null`, and runs from **cwd `~/.config/litellm`**, where Phase 4a also deploys `linux/configs/litellm-pyproject.toml` → `pyproject.toml` — prisma-client-py's per-cwd config, the only lever for its list-typed `nodeenv_extra_args` (`PRISMA_NODEENV_EXTRA_ARGS` fails pydantic v2's list parse) — pinning the private nodeenv to **Node LTS** (`--node=lts`, applied when the nodeenv is (re)installed; nodeenv's default is the newest *Current* release, days old). The unit's `WorkingDirectory` is that dir. Phase 4a **never starts the unit itself**: it stops + runtime-masks it for the venv/toolchain work and unmasks at the end; the run's single start is Phase 7's (after the `pg_isready` gate, against the freshly deployed unit/env/config), so the start arc is never paid twice. Engines are fetched **by the CLI on demand** (`--version` / `generate`) from `binaries.prisma.sh` into `~/.cache/prisma/master/<hash>/<target>/` and copied into `node_modules/@prisma/engines/` — not by npm's `@prisma/engines` postinstall, which the overlays' `~/.npmrc` (`ignore-scripts=true`) disables; with that cache populated neither call touches the network, so the heals' `rm -rf node_modules` is safe. **A generate failure is non-fatal**: `LITELLM_CLIENT_BROKEN=1` keeps the unit *stopped* at every start site (4a restore, Phase 7 — a start would crash-loop 20× on "The Client hasn't been generated yet"), the run continues (an overlay's later phases too), a red end-of-run banner says what to do, and the next run's import probe regenerates. The **fastapi ceiling** (`LITELLM_FASTAPI_GUARD`, applied via the shared `LITELLM_UV_WITH` array) works around BerriAI/litellm#35763: fastapi 0.140.7 removed `get_flat_dependant` (fastapi/fastapi#16076), which litellm ≥1.95.0's `management_v1` imports at startup — with fastapi ≥0.140.7 the proxy dies on import in ~650ms and systemd latches `start-limit-hit`; litellm's own bound (`fastapi>=0.136.3,<1.0`) doesn't exclude it. The fix (PR #35773, `get_flat_params`) merged 2026-08-09 but missed 1.95.1, 1.96.0, **1.96.2 and 1.97.0** (shipped wheels verified still-broken, last checked 2026-08-19). **Verify by grepping the wheel, never by comparing SHAs** — #35773 landed on `litellm_internal_staging`, so `git compare ecba48d...<tag>` reads "diverged" for *every* release tag and settles nothing; instead `pip download litellm==<ver> --no-deps --only-binary=:all:` then `unzip -p …whl litellm/proxy/management_endpoints/management_v1/common.py | grep get_flat_` — `get_flat_params` means fixed, `get_flat_dependant` means still broken. (#35763 is the *issue*, #35773 the PR; both numbers are correct, they are different objects.) **Drop the guard once a release containing merge `ecba48d` has aged past the uv cooldown** — Phase 4a `warn`s when litellm exceeds `LITELLM_FASTAPI_GUARD_STALE_ABOVE` (newest release verified still-broken), so the pin can't rot silently. **Skipped under `--docker`** (the `ghcr.io/berriai/litellm` image bundles LiteLLM + a generated Prisma client). The `>=1.84.0` **floor** (not a hard pin) sits above the compromised 1.82.7/1.82.8 PyPI releases (so the old explicit `!=` excludes are gone) and guarantees the reasoning support this setup relies on for GPT-5.6: the Anthropic→Responses adapter honours `output_config.effort` (verified present at the `v1.84.0` tag). The chat→Responses auto-route (1.83.0+) is no longer the mechanism — the `openai/` route takes the dedicated adapter instead |
| 4b | Claude Code via official installer when missing, else `claude update` (upgrade in place); always runs. Then `prune_claude_versions` (common.sh) trims `~/.local/share/claude/versions` to the **active binary only**. Claude Code sweeps that dir itself on startup, but keeps `VERSION_RETENTION_COUNT=2` (compile-time constant — no env var, no settings key) **plus** every protected version (running executable, `~/.local/bin/claude` symlink target, live-locked files), so its floor is three ~300 MB binaries ≈ 900 MB — and the overlays' post-update `claude install stable` pin keeps the symlink target out of the two newest, which is what pins it at three. The prune skips `*.tmp.*` (in-flight installs, reaped by upstream's own 1h rule) and any binary that is a running process's `exe`. **Precondition, same as upstream's:** the launcher must be a symlink into the versions dir; when it isn't, Claude Code silently disables its own cleanup ("the launcher … is externally managed") *and* `claude install` refuses to replace a launcher it doesn't own, so the prune deletes nothing and warns instead — the fix is to delete the file and re-run the install |
| 4c | (only with `--install-obsidian`) ACP adapter via `bun add -g` (install-if-missing) |
| 4d | (only with `--install-obsidian`) latest Obsidian amd64 `.deb` resolved from the GitHub releases API via `jq`, downloaded with `download_to_file` (retrying `curl_secure`) and installed via `apt_install` (apt resolves deps). install-if-missing (skips if `dpkg-query` reports `obsidian` as `install ok installed`); failures non-fatal |
| 4e | (all modes) [`blaude`](https://github.com/c0ffee0wl/blaude) — a single-file Bash wrapper that runs Claude Code inside a bubblewrap sandbox (for autonomous `--dangerously-skip-permissions` operation). Re-fetch the raw `main` script with `download_to_file` (retrying `curl_secure`) → `~/.local/bin/blaude` (shebang-checked, atomic `mv`, chmod 0755; failures non-fatal — keeps existing). **Always re-fetched = install + update** (not install-if-missing): blaude is a rolling script with no release tags and no self-update (`blaude update`/`install` pass through to `claude`), so re-fetch is the only update path — same upgrade-in-place spirit as bun / LiteLLM / `claude update`. Runs in **every** mode: its only deps (`bwrap` Phase 2, `claude` Phase 4b) install in all modes. The `osc52-clipboard` companion is **deliberately not** installed, and **no `claude` alias** is set (the drop-in `alias claude=blaude` stays opt-in) |
| 5a | gateway URL + master key (as `ANTHROPIC_AUTH_TOKEN` and `LITELLM_API_KEY`) + telemetry opt-outs + `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` + `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` + `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT` + `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS,FABLE}_MODEL` → `~/.profile` (kept here, not managed-settings, so user can `unset` for `--dangerously-skip-permissions` and so `--router-only` gets them without root). The four default-model vars resolve to `azure/gpt-5.6-{terra,luna,sol}` (haiku → luna, sonnet/opus → terra, fable → sol; the fable slot needs CC ≥2.1.170, which the every-run `claude update` guarantees) when both `AZURE_OPENAI_API_KEY` and `AZURE_RESOURCE_ENDPOINT` are set in `.env` — that Azure branch also writes `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000` + `CLAUDE_CODE_DISABLE_1M_CONTEXT=0`, the undocumented pair that raises CC's believed context window for these unrecognized ids from 200K to 1M (see the context-window bullet under *Model naming*; scrubbed with the other gateway levers under `--install-only`); otherwise they're written empty (any prior non-empty value in `~/.profile` is preserved across re-runs) and a yellow end-of-script banner instructs the user to add a model via `/ui` and fill them in. Thinking/effort for the non-`claude-*` ids need no capability declarations: Claude Code sends `thinking:{"type":"adaptive"}` to model ids it doesn't recognize (gateway protocol reference), and `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT=1` — the documented gateway lever for custom identifiers — makes the effort parameter ride along in `output_config`. The formerly-written `ANTHROPIC_DEFAULT_*_MODEL_SUPPORTED_CAPABILITIES` trio is **retired and scrubbed**: capability declarations are inert behind an `ANTHROPIC_BASE_URL` gateway (the protocol reference scopes them to `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY,MANTLE}`; re-add only if the box moves to one of those). Effort *values* are normalized LiteLLM-side: its map declares `supports_xhigh_reasoning_effort: true` for `gpt-5.6-{sol,terra,luna}` (xhigh runs as real xhigh), while `max` still clamps to xhigh (no `supports_max_reasoning_effort` map flag; BerriAI/litellm#26111 — revisit if it lands). Also scrubs `IS_DEMO` from `~/.profile` + current shell (anthropics/claude-code#37780), the retired `VSCODE_TELEMETRY_DISABLE`/`VSCODE_CRASH_REPORTER_DISABLE` pair (community folklore — nothing in VS Code reads them; the real control is the `telemetry.telemetryLevel` setting / enterprise `TelemetryLevel` policy, vscode-setup's domain), and the retired `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` umbrella — replaced in the managed env block by its four documented components (`DISABLE_AUTOUPDATER`/`DISABLE_FEEDBACK_COMMAND`/`DISABLE_ERROR_REPORTING`/`DISABLE_TELEMETRY`) because the umbrella disables gateway model discovery at **any** value, even `"0"` (presence-triggered; anthropics/claude-code#61112), while the individual flags don't. Also writes two all-mode UX prefs: `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=75` (currently **inert** here: per the env-vars doc it only applies when compaction is proactive — cloud sessions, Sonnet/Opus 4.6, or `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set, none of which holds on this gateway path; kept as a self-activating forward-compatible pref that can only *lower* the threshold, anthropics/claude-code#31806) and `CLAUDE_CODE_FORK_SUBAGENT=1` (let Claude spawn **forked** subagents — a subagent that inherits the *full* session context (same model/tools/history) instead of a fresh one; v2.1.117+, honored in interactive/headless/SDK/`claude -p`). The manual `/fork` command already works without it (default v2.1.161+); the var additionally lets Claude auto-spawn the `fork` type and routes all subagent spawns to background (already the v2.1.198 default). **Model-agnostic**: the fork inherits the session's gateway id (`azure/gpt-5.6-terra`) — no hardcoded `claude-*` id, so no 404 (unlike the `CLAUDE_CODE_SUBAGENT_MODEL` alias footgun). Caveat on this gateway: the advertised cost win (a fork reuses the parent's **Anthropic prompt cache**) is cache-specific — over LiteLLM→Azure, Claude Code's `cache_control` isn't the mechanism, so a fork degrades to a normal full-context request (functional, but no guaranteed savings). Under `--router-only`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is **not** set (removed if present) so a dev box's Bash/MCP/hooks subprocesses keep the full env (incl. the gateway token). The CC feature/privacy toggles (`DISABLE_AUTOUPDATER` … `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`) are **single-sourced** from `claude-managed-settings.json`'s `env:` block — an add/edit there lands in `~/.profile` automatically on the next run (the mirror only accumulates: retiring a toggle additionally needs a `remove_profile_export` scrub, like `IS_DEMO`). Under `--no-profile-toggles` the mirror + the explicit toggle writes flip to scrubs (see the flag bullet above) |
| 5b | provider secrets from `.env`/shell/`~/.profile` + master key → in-memory `LITELLM_ENV_CONTENT` (written to disk in Phase 6). Uses `collect_litellm_provider_vars` |

## Key Conventions

- **Idempotency**: every phase is safe to re-run, and a no-op re-run stays cheap: the apt round-trips (index refreshed at most once per run), the ~/.profile rewrites, and the claude-devtools restart are all skipped when nothing changed. One deliberate exception: native-mode litellm is bounced **once** per run — Phase 4a's stop-window has to close before knowing whether uv will mutate the venv (uv has no dry-run for tool installs, and probing litellm's own version wouldn't catch dependency-only upgrades, which rebuild the venv too), so every run pays one stop + one start (~20-30s to liveliness on a warm box). Phase 7 never adds a second restart to an unchanged unit.
- **Tool update policy**: bun, uv, LiteLLM, and Claude Code upgrade **in place on every run** (`bun upgrade`, `uv self update`, `uv tool install --upgrade`, `claude update`), and blaude is re-fetched from `main` (a rolling script with no releases). Everything else is **install-if-missing** — ACP, Obsidian, pnpm, the `nah` plugin, Docker CE are not touched when present, and the pinned artifacts (claude-devtools release tag, the `--docker` image tag) only advance deliberately.
- **Profile management**: use `update_profile_export` in `common.sh` for env-var changes — it writes to `PROFILE_FILE` (`~/.profile`; deliberately a single constant, no multi-file machinery). Never edit profile files with raw `sed`/`echo`. Never write provider secrets here — they belong in `~/.config/litellm/env`.
- **systemd template substitution**: service files in `linux/systemd/` use `__PLACEHOLDER__` tokens (`__LITELLM_BIN__`, `__APP_DIR__`, `__PORT__`, `__ENV_FILE__`, `__PATH__`). `deploy_user_systemd_service` in `common.sh` runs `sed` over them before `write_if_changed`. The docker-compose template (`linux/configs/litellm-docker-compose.yml`) is rendered the same way in Phase 7 — `__PORT__` is its only token, so `LITELLM_PORT` governs the native unit and the container alike. `deploy_user_systemd_service` refuses to install a render that fails, comes out empty, or still contains a `__TOKEN__` — it returns 1 (same as "unchanged") so the caller leaves the previous unit in place rather than daemon-reloading against a broken one.
- **Restart policy for long-lived user services**: all three units (`litellm.service`, `litellm-docker.service`, `claude-devtools.service`) use `Restart=always`, **not** `on-failure`. `on-failure` ignores a clean exit, and both a bun HTTP server (claude-devtools) and `docker compose up` exit 0 in ordinary circumstances; the overlay repos that consume this installer (ct-kali-llm, ct-dfir-llm) run setup.sh manually with no daily timer, so a unit that exited 0 would stay down until a human noticed. `always` also gives `inactive` exactly one meaning — a *commanded* stop, which systemd never restarts — so Phase 7's native↔docker switch (`stop_user_service litellm`; the stop is unconditional, since `is-active` misses `activating`/`failed` — see the helper's docstring) still tears the unit down and keeps it down. The two litellm variants must keep identical policy: Phase 7 deploys either template under the same `litellm` unit name.
- **`StartLimitBurst=20` / `StartLimitIntervalSec=600` on the litellm units**: a `--user` unit cannot order against the *system* `postgresql@.service`, and the `After=network-online.target` line orders nothing because that target does not exist in the user manager — so LiteLLM races Postgres at boot and needs enough retries to outlast it. The race itself is defused by the units' bounded `ExecStartPre` pg_isready gate (below): without it, every boot-time retry cycle cost a full proxy import + two Node spawns against a dead socket (~60–120s of single-core churn per cycle, observed 2026-08-20 on a slow VM); with it, waiting costs 5ms probes and the start arc runs once, after Postgres answers. StartLimit remains insurance, not the fix (the fix for a cluster that never comes up is the unconditional `systemctl enable --now postgresql@<ver>-main` in Phase 6). **Raise the two numbers together.** systemd gives up only when `Burst` starts land inside `IntervalSec`, i.e. at a restart cycle shorter than `IntervalSec/Burst` — so widening `Burst` alone *narrows* the give-up envelope: 10/300s gave up below a 30s cycle, and 20/300s would only give up below 15s. Combined with `Restart=always` that would make any 15–30s crash-loop retry forever, which is exactly the band the unit's own comment describes (the startup Prisma schema push + engine fetch take 15–25s). 20/600s keeps the 30s envelope while still granting all 20 attempts to a fast loop, so a permanently broken box still parks in `failed` instead of respawning uvicorn + Prisma indefinitely — and on the docker unit, whose `ExecStartPre` re-pulls per start, that also bounds the registry round-trips. `claude-devtools.service` keeps `5`/`60s` (a 12s envelope) — it has no DB dependency and one cheap bun spawn per cycle.
- **Postgres readiness gate (`ExecStartPre` in both litellm units)**: the native equivalent of upstream's compose `pg_isready` healthcheck + `depends_on`. A bounded loop (`for _ in $(seq 60) … pg_isready -q -h /run/postgresql -p <port>; sleep 2` — `$$` in the unit file is systemd's literal-$ escape) probes the host socket for ~120s, then **falls through with exit 0** so an absent DB degrades to the pre-gate behavior and can never fail the unit — the gate only delays, never blocks. `TimeoutStartSec` (180s native / 300s docker, which must also cover the image pull) bounds `ExecStartPre` and must stay above the loop ceiling. Phase 7 renders `__PGPORT__` from the live cluster's `pg_setting port`; on an **external** `DATABASE_URL` the line is deleted instead (remote DBs aren't probeable by local pg_isready, and `deploy_user_systemd_service` refuses renders with leftover tokens). The docker unit probes host-side too — the container reaches Postgres over the same bind-mounted socket, so the host probe is exact.
- **DB schema posture is `db push`, not `migrate deploy`**: both runtimes pass `--use_prisma_db_push` (litellm.service `ExecStart` + the compose `command:` list; flag verified present and default-off at both the v1.93.0 docker pin and 1.96.2). Without it, litellm's default runs the litellm-proxy-extras migration machinery on **every service start** against its ~141 shipped migrations, and on any DB whose `_prisma_migrations` history doesn't match (e.g. one provisioned in the db-push era, or a half-converged one) that degenerates into per-migration `migrate resolve`/`db execute` recovery — each a ~1s Node spawn, minutes of >100% CPU before uvicorn binds, converging only if one pass runs uninterrupted, which the update flow's restarts prevent. `db push` is litellm-core's own alternative: one `prisma db push --accept-data-loss --skip-generate` subprocess, `timeout=60`, 4 attempts, seconds typical, **ignores migration history entirely** — bounded and idempotent on every box regardless of DB provenance. Accepted trade-offs: `--accept-data-loss` is upstream's own invocation (a schema litellm wholly owns, single box); no migration history accrues, so reverting to migrate posture later means deleting the flag *and* baselining — one `db push`, then `migrate resolve --applied` per shipped migration
- **Master-key strategy**: a `sk-<48 hex chars>` master key is auto-generated on first run via `openssl rand -hex 24`, written to `~/.config/litellm/env` (as `LITELLM_MASTER_KEY`) and to `~/.profile` (as `ANTHROPIC_AUTH_TOKEN` and `LITELLM_API_KEY`). All three names point at the same value. Re-runs preserve it via `read_profile_export`. Setting `ANTHROPIC_AUTH_TOKEN=sk-…` in `.env` overrides auto-generation. Phase 6 also writes `LITELLM_SALT_KEY` to the env file (persisted across reruns like the DB password, **never regenerated**): it encrypts /ui-added models' provider credentials at rest — without it litellm signs them with the *master key*, welding credential encryption to the admin credential so a master-key rotation would brick every stored model. First write deliberately seeds from the master key **already in `~/.config/litellm/env`** — i.e. the one the deployed service last ran with, which is what encrypted existing rows under the master-key fallback, so the write is a cryptographic no-op (a fresh box with no env file falls back to the current key). Reading it from the file rather than the in-run `ANTHROPIC_AUTH_TOKEN` matters because a run that *also* rotates the master key would otherwise pin the salt to a key those rows were never encrypted with — after that the master key is free to rotate. **Never rotate the salt key** — there is no re-encryption flow; changing it makes stored credentials unreadable. **Never export `ANTHROPIC_API_KEY` in `~/.profile`/shell rc files on a gateway box**: Claude Code prefers a non-empty `ANTHROPIC_API_KEY` over `ANTHROPIC_AUTH_TOKEN` (sent as `x-api-key`; env-vars doc) → 401 at LiteLLM. Keep it in `.env` — the Phase 5b collector still delivers it to `~/.config/litellm/env` for a real-Anthropic upstream. Phase 5a warns via an end-of-run banner when it spots a non-empty export in `~/.profile`/`~/.bashrc`/`~/.zshrc` (warn-only, gateway modes only — scrubbing would destroy the collector source, and `--install-only` boxes may legitimately export the key).
- **Model naming**: the baseline `litellm-config.yaml` deliberately uses upstream provider-prefixed ids as Public Model Names (`azure/gpt-5.6-terra`, `azure/gpt-5.6-luna`, `azure/gpt-5.6-sol`) — no `claude-*` alias layer. Claude Code asks for those ids directly via `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS,FABLE}_MODEL` in `~/.profile`. Trade-offs accepted by this choice:
  - **Why the `openai/` route, not `azure/`**: `litellm_params.model` is `openai/gpt-5.6-*` even though the traffic lands on Azure. This is load-bearing, not a typo. LiteLLM's `/v1/messages` handler picks the purpose-built Anthropic→Responses adapter only when `custom_llm_provider == "openai"` — `_RESPONSES_API_PROVIDERS = frozenset({"openai"})` in `litellm/llms/anthropic/experimental_pass_through/messages/handler.py` (verified byte-identical at `v1.84.0`, `v1.93.0`, `v1.94.0` and `main` — i.e. across the whole range from this repo's floor to current upstream, so the behaviour is not a version quirk). LiteLLM's published docs and its own in-repo comment both claim OpenAI **and Azure** take that path; the frozenset says otherwise. Under `azure/`, Claude Code's traffic instead goes Anthropic→chat-completions and reaches `/responses` only through the conditional fallback in `main.py::responses_api_bridge_check`, which needs **both** `reasoning_effort` and `tools` — so background and Haiku-tier work (auto-compact summarization, conversation titles, quota pings) silently stays on Chat Completions and loses reasoning-item continuity across tool turns, reasoning summaries, and `reasoning_effort=max`. The `openai/` route makes Responses unconditional. Tool schemas are unaffected: the adapter emits `{"type":"function","name":…,"parameters":…}` straight from Anthropic's format — already flat, which is what Azure wants (the nested shape LiteLLM's *Azure* config has to flatten only arises on the chat path). **The route also drives cost tracking, and that needs an explicit override.** Left alone, prices resolve off `litellm_params.model` → the **OpenAI** map keys `gpt-5.6-{terra,luna,sol}`, i.e. OpenAI list prices for traffic Azure invoices (understating terra 1.38×, luna 5.50×, sol 1.10×). So each deployment carries an explicit rate set under `model_info` (`input_cost_per_token`, `output_cost_per_token`, `cache_read_input_token_cost` + their `_above_272k_tokens` variants) — any `_CUSTOM_PRICING_KEYS` member sets `custom_pricing=True` (`litellm_logging.py::use_custom_pricing_for_model`), which routes costing through the deployment's own registered entry and bypasses the map lookup. **`model_info.base_model: azure/eu/gpt-5.6-<tier>` is the obvious fix and does not work here — verified against 1.93.0, do not re-try it.** `_select_model_name_for_cost_calc` *does* return the `azure/eu` key, but the downstream lookup passes the route's provider alongside it and `get_model_info("azure/eu/gpt-5.6-luna", custom_llm_provider="openai")` raises `This model isn't mapped yet` (that entry's `litellm_provider` is `azure`); the cost calculator swallows it and silently falls back to the OpenAI entry. `base_model` can only name a key whose provider matches the route's, so it is unusable behind `openai/`. The rates are Azure **Data Zone Standard, EU zone** (Sweden Central is inside the Azure EU Data Boundary). **The numbers live in `litellm-config.yaml` only** — its comment block carries the $/1M table and the date they were verified, and the `update-azure-openai-prices` skill (`.claude/skills/`) refreshes both from Azure's public retail feed. Deliberately not restated here: this bullet went stale the first time it carried figures, and a second copy buys nothing a `grep` does not. Two things worth knowing without opening the config — Azure had **not** followed OpenAI's 2026-07-30 cut (terra −20%, luna −80%, sol flat) as of this writing, which is why luna costs 5.5× its OpenAI list price; and a deployment-type or zone move changes every rate, so run the skill after one. Trade-off accepted: no `api_version` pinning, no Azure AD token auth, no Azure-specific error mapping — none of which this repo uses (API-key auth only). **The `azure/` prefix on the Public Model Names is a label naming the destination cloud, not the provider route.**
  - **`azure/gpt-5.6-sol` is the `fable` tier, never auto-selected**: `ANTHROPIC_DEFAULT_FABLE_MODEL` (Phase 5a) points the `fable` alias at it — the fourth model-tier slot, CC ≥2.1.170: "Model ID that the `fable` alias resolves to, and the ID Claude Code recognizes as Fable 5 for automatic model fallback on third-party providers" (env-vars doc). No background path uses the fable alias, so it costs nothing unless you ask for it with `/model fable` (or the full id, or subagent frontmatter `model: fable`). Two consequences. (1) It needs a `gpt-5.6-sol` Azure deployment; without one that id 404s at call time and nothing else is affected (LiteLLM does not validate deployments at boot, and the id still appears in `/v1/models`). (2) **Thinking and effort work on it without per-id config** — Claude Code treats model ids it doesn't recognize as current models and sends `thinking:{"type":"adaptive"}` optimistically, and `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT=1` (Phase 5a) covers effort session-wide. The `fable` alias already reaches it from the `/model` picker; the `ANTHROPIC_CUSTOM_MODEL_OPTION` escape hatch below remains for other single-name entries.
  - **Gateway-discovery picker auto-population is off** for the baseline entries — and, today, for everything else too. Claude Code's `/v1/models` discovery (CC ≥2.1.129, opt-in via `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` in `~/.profile`) filters on names starting with `claude` or `anthropic` (<https://code.claude.com/docs/en/llm-gateway-protocol#model-discovery>); upstream-prefixed names never match. Beyond the name filter there were two gates: (1) **CC-side** — `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` at **any** value (even `"0"`; presence-triggered) disables the fetch entirely (anthropics/claude-code#61112). This repo replaced the umbrella with its four documented components in the managed env block and scrubs it from `~/.profile`, so that gate is now open (caveat: a box flipped full → `--router-only` keeps the stale umbrella in the root-owned `/etc/claude-code/managed-settings.json` — Phase 8a is skipped there and managed env wins over the profile scrub — so discovery stays blocked until a full/harden re-run refreshes that file). (2) **LiteLLM-side** — CC parses only the Anthropic-native models envelope, which LiteLLM serves (via `anthropic-version` content negotiation) only from **≥1.95.0** (BerriAI/litellm#30273, merged 2026-06-17; absent from the `v1.93.0` docker pin and from `v1.94.0` = PyPI latest as of 2026-07-30). Native installs cross that line automatically on a future re-run's upgrade-in-place; `--docker` needs a deliberate pin bump. The baseline entries still route fine — typing `/model azure/gpt-5.6-luna` always works.
  - **Feature gates resolve optimistically for unrecognized ids** — with one real gap. Thinking needs nothing: per the gateway protocol reference, Claude Code sends `thinking:{"type":"adaptive"}` for Claude 4.6+ **and treats model names it doesn't recognize, such as gateway aliases, as current models that receive the field**; LiteLLM's Anthropic→Responses adapter converts it (reading `output_config.effort` when present) into Responses-API reasoning. Effort needs one lever: `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT=1` (Phase 5a), documented exactly for gateways serving custom identifiers. The `ANTHROPIC_DEFAULT_*_MODEL_SUPPORTED_CAPABILITIES` trio this repo once wrote is **inert behind an `ANTHROPIC_BASE_URL` gateway** (protocol reference: capability declarations apply only under `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY,MANTLE}`) — Phase 5a scrubs it now. The last gate is **context-window belief**: CC assumes 200K for an unrecognized id while the gpt-5.6 tiers take 1.05M input. No *documented* knob raises it — `CLAUDE_CODE_AUTO_COMPACT_WINDOW` is "capped at the model's actual context window" (= the believed 200K; lower-only) and the `[1m]` suffix works on built-in names only (anthropics/claude-code#68522) — but the **undocumented pair `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000` + `CLAUDE_CODE_DISABLE_1M_CONTEXT=0` does** (from the #68522 thread; the same mechanism third-party gateway docs use, e.g. Kimi's 1048576). Phase 5a writes it on the Azure path — deploy-verified 2026-07-30: statusline and auto-compact base flip from 200K to 1M. Caveat: the value is **session-global**, not per-model — safe here because all three served tiers take 1.05M input, but a `/ui`-added smaller-window model would be over-believed (API 400s before compaction fires); adjust or unset it in that case. `CLAUDE_CODE_AUTO_COMPACT_WINDOW` stays unset, and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=75` remains inert (its proactive-compaction conditions still don't hold).
  - **To get auto-discovery back for a UI-added model**, give it a `claude-*` or `anthropic-*` Public Model Name (e.g. `claude-gemini-3-pro` → `gemini/gemini-3.0-pro`, key `os.environ/GEMINI_API_KEY`). `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` is on in `~/.profile`, so such an entry appears in `/model` automatically **once the deployed LiteLLM is ≥1.95.0** (the LiteLLM-side gate above); until then, add it with `ANTHROPIC_CUSTOM_MODEL_OPTION`.
  - **Escape hatch for single-name picker entries**: set `ANTHROPIC_CUSTOM_MODEL_OPTION=<name>` (plus optional `…_NAME` / `…_DESCRIPTION`) in `claude-managed-settings.json`'s `env:` block (which Phase 5a also mirrors into `~/.profile`, so the entry applies under `--router-only` too). Adds one custom picker entry regardless of name shape — useful for pinning the headline upstream id in the picker. No `…_SUPPORTED_CAPABILITIES` companion needed — only `…_NAME`/`…_DESCRIPTION` take effect over a gateway; thinking/effort are covered as described under the feature-gates bullet above.
  - **No-Azure install path**: leaving `AZURE_OPENAI_API_KEY` / `AZURE_RESOURCE_ENDPOINT` blank in `.env` (or omitting `.env` entirely) is supported — setup still completes, the four `ANTHROPIC_DEFAULT_*_MODEL` exports in `~/.profile` are written empty (Phase 5a; see also the Azure section in `.env.example`), and a banner at the end of `setup.sh` tells the user to add a model via `http://127.0.0.1:4000/ui` and set the vars manually. The `CLAUDE_CODE_MAX_CONTEXT_TOKENS` pair is **not** written on this path (the `/ui` model's window is unknown) — set it manually to your model's input limit if it exceeds 200K. Re-runs preserve any non-empty value already in `~/.profile`.
  - **Why `ANTHROPIC_SMALL_FAST_MODEL` + `CLAUDE_CODE_SUBAGENT_MODEL` are intentionally NOT set**: the `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS,FABLE}_MODEL` quartet is the complete set — neither extra var is needed, and both are footguns here. (1) `ANTHROPIC_SMALL_FAST_MODEL` is **deprecated in favor of `ANTHROPIC_DEFAULT_HAIKU_MODEL`** (code.claude.com/docs/en/model-config env-var table), whose own doc line is *"the model to use for `haiku`, or background functionality"* — so `azure/gpt-5.6-luna` (Phase 5a) already drives the background/small-fast path (auto-compact summarization, titles, quota calls) **and** the built-in `Explore` subagent (hardcoded `haiku`, resolves through the same var). (2) `CLAUDE_CODE_SUBAGENT_MODEL` is real but blunt: per the same table it **overrides both the per-invocation `model` param AND a subagent's `model:` frontmatter** (`inherit` = normal resolution). Left unset (our default), subagent model resolution already terminates at gateway ids — frontmatter `model: sonnet/opus/haiku/fable` resolves the alias through the `ANTHROPIC_DEFAULT_*` quartet → `azure/gpt-5.6-{terra,luna,sol}`, and `inherit`/no-frontmatter uses the main session model (also a gateway id). So there is **no unset-failure mode**: nothing leaks a hardcoded `claude-*` id for LiteLLM to 404 on. Setting it would flatten per-agent tier choices, and the table requires a **full model name** — a bare alias 404s (`CLAUDE_CODE_SUBAGENT_MODEL=sonnet` → `404 not_found_error: model: sonnet`, anthropics/claude-code#9573). Only set it for a deliberate cost play (force *all* subagents onto the cheap tier: `CLAUDE_CODE_SUBAGENT_MODEL=azure/gpt-5.6-luna`, never a bare alias).
- **Managed-settings token substitution**: `linux/configs/claude-managed-settings.json` contains a `__REPO_DIR__` token (used by `hooks` paths). setup.sh Phase 8a substitutes via `sed` before sudo-installing to `/etc/claude-code/managed-settings.json`. `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` deliberately live in `~/.profile` only (not managed-settings) so the user can point at a remote router without root.
- **Telemetry**: the systemd unit pins `LITELLM_MODE=PRODUCTION`, `LITELLM_LOG=ERROR`, and passes `--telemetry False`. Per LiteLLM docs, self-hosted instances do not phone home, but we set the flag defensively. `LITELLM_LOCAL_MODEL_COST_MAP` is deliberately left unset so LiteLLM refreshes `model_prices_and_context_window.json` from `BerriAI/litellm@main` on every start — without this, the UI's "Add Model" provider dropdown is capped at the catalog frozen into the installed wheel (e.g. no `gpt-5.3` until you `uv tool upgrade litellm`). Tradeoff: a small GitHub fetch at boot.
- **Hardening boundaries**: this repo intentionally does **not** ship `bunfig.toml`/`npmrc`/`uv.toml`/`pip.conf`. Supply-chain hardening lives outside this repo.
- **Docker mode (`--docker`)**: an opt-in alternative runtime for **LiteLLM only** — Postgres stays a host system service and claude-devtools stays native. `install_docker_rootless` (common.sh) installs Docker CE and configures it **rootless** (`dockerd` as `systemd --user`); rootless is deliberate because adding the user to the `docker` group grants effective root via the daemon socket, which would undercut the managed-settings/sandbox/exit-2-hook posture. A pre-existing **rootful** daemon is coexisted-with, never disabled (the "user's call, not a silent side effect" stance documented in `install_docker_rootless`): when its socket is detected the setuptool gets `--force` so rootless installs alongside it on a separate per-user socket, and the litellm unit pins `DOCKER_HOST` to that rootless socket regardless of the default CLI context. The container is litellm only (`linux/configs/litellm-docker-compose.yml`, deployed to `~/.config/litellm/docker-compose.yml`), published **loopback-only** (`127.0.0.1:4000:4000`; the container listens on `0.0.0.0` so the mapping works, but it's never reachable off-host), mounting `./config.yaml` + `./env` (the same mode-600 env file the native unit uses). Image is a **pinned** `ghcr.io/berriai/litellm:vX.Y.Z` tag (currently `v1.96.2`) — bumped deliberately on a git edit + re-run, like the claude-devtools tag pin (a floating `latest`/`main-stable` would auto-roll-forward on the unit's `ExecStartPre` `docker compose pull`, against the no-auto-update convention). setup.sh's foreground pre-pull is skipped once the pinned image is in the local cache (`docker image inspect`) — `--docker` re-runs don't hit ghcr.io; a tag bump misses the cache and pulls. This pins LiteLLM's **plain per-release tag**, *not* the `-stable` channel: `-stable` tags are promoted later and **lag** (newest is `v1.83.14-stable`, *below* the native uv `>=1.84.0` floor — no `-stable` image exists for 1.84+), so a `-stable` pin can't match that floor. `v1.96.2` clears it, sits above the compromised 1.82.7/1.82.8, carries the Responses-adapter support this setup relies on for GPT-5.6, and **matches the native `uv` resolution** (both runtimes at 1.96.2 as of the 2026-08-20 bump; the four verification criteria and their measured answers are recorded in the compose template's pin comment). **When bumping, verify four things — they can diverge**: (1) the tag is aged in past the cooldown, (2) it is git-tagged upstream (auditable source), (3) for a ≥1.95.0 tag, the image's bundled fastapi is <0.140.7 **or** the build contains upstream merge `ecba48d` (BerriAI/litellm#35763 — the native Phase 4a fastapi guard does not reach inside the image), and (4) the image exists on ghcr.io (`curl -s "https://ghcr.io/token?scope=repository:berriai/litellm:pull"` → token → manifest HEAD; a given version's `-stable` variant may not exist, which yields a `not found` pull error). Counter-example from the `v1.93.0` bump: **1.93.1 was on PyPI and ghcr.io but had no upstream git tag at all**, shipped same-day, and post-dates 1.94.0 — a backport lane, not mainline. Picking it would have pinned the container to unauditable, un-aged source. **Host-DB connectivity uses the Unix socket, not TCP** — no longer docker-specific (native mode uses the same socket URL since the socket switch; see the Phase 6 row), but for the container it is additionally backend-independent (no reliance on rootless host-loopback / `host.docker.internal`): the host Postgres socket dir `/run/postgresql` is bind-mounted into the container and `DATABASE_URL` carries `?host=/run/postgresql`, so Postgres keeps its default loopback-only/socket binding and **nothing is exposed on any network interface**. The only host-side change is a scoped pg_hba line — `ensure_pg_socket_scram_rule` (common.sh, called from Phase 6) inserts `local litellm litellm scram-sha-256` above Debian's default `local all all peer` (idempotent; first-match-wins; reloads Postgres) because peer auth can't map the container's UID to the `litellm` role. We deliberately avoid `listen_addresses='*'` and never add a TCP `pg_hba` rule. Because the host DB is reused (not a fresh container volume), `/ui`-added models, keys, and spend history persist across a native↔docker switch. Footprint vs native: ~+2.4 GB disk (engine + ~2 GB image), ~+0.3–0.4 GB runtime RAM (container + rootless dockerd/containerd/slirp4netns); build-time RAM unaffected (nothing builds — claude-devtools' image isn't built on-host, sidestepping the vite OOM the ≥3.5 GB Phase 9 gate guards). The `litellm` user-service name is reused for both runtimes, so a re-run with/without `--docker` swaps `ExecStart` on the next `systemctl --user restart litellm`.
- **The Postgres socket URL protects against port capture, not against a dead cluster — keep the docs honest about which**: the incident it exists for is a Docker container publishing host 5432 (docker-proxy) while the TCP URL pointed there — Prisma then talks to the wrong backend and `migrate deploy` times out in a 60 s loop with the unit still `active (running)`. The socket URL is immune to that *capture* (a published port cannot touch `/run/postgresql/.s.PGSQL.<port>`), and the `SHOW port` derivation keeps a cluster that *drifted* to 5433 (created/moved while something else held 5432) reachable — including making "move Postgres to another port + re-run setup.sh" a complete repair. What it does **not** survive: a container grabbing 5432 *before* the cluster starts, with both loopback address families bound — the postmaster then fails every TCP bind and exits FATAL ("could not create any TCP/IP sockets"), so the Unix socket is never created either; no client-side transport survives a dead server (if only one address family is taken, the cluster starts and the socket path wins). Full immunity would be `listen_addresses = ''` (socket-only server, nothing to collide with) — **considered and deferred**: it changes the server's posture for every other local TCP client, not just LiteLLM's connection. Revisit only if the bind-FATAL shape is actually observed in the field. When testing the protection, use the drift shape (cluster on 5433, container on 5432), never "restart Postgres while a container holds 5432" — that is the bind-FATAL shape and nothing passes it
- **Sandbox control**: the entire `sandbox` block lives in the **user** file (`linux/configs/claude-settings.json` → `~/.claude/settings.json`), not managed-settings. This is deliberate so `/sandbox` actually works: per Claude Code's precedence, a sandbox **boolean** in managed settings (`enabled`, `failIfUnavailable`) is used verbatim and *ignores* any user/local value, so `/sandbox` (which writes `.claude/settings.local.json`) is inert whenever `sandbox.enabled` sits in managed — at any value, including `false` (confirmed behaviour; the picker also desyncs on custom sandbox blocks, anthropics/claude-code#47624). The template ships `enabled:true` (ON by default; `/sandbox` can toggle it off, local scope overriding the user default), `autoAllowBashIfSandboxed:true`, and the credential/network floor (`filesystem.denyRead`/`denyWrite`, `network.allowedDomains`/`deniedDomains`). `failIfUnavailable` is **omitted** (default `false`), so a box where bwrap can't run (e.g. a kernel with user namespaces disabled) warns + runs unsandboxed instead of refusing to start. `allowUnsandboxedCommands` is set to **`false`** (stricter than the `true` default — the `/sandbox` Overrides tab labels this **Strict sandbox mode**): the per-command `dangerouslyDisableSandbox` escape hatch is disabled (the parameter is completely ignored), so a sandboxed command must run sandboxed or not at all (barring an `excludedCommands` entry). Deployed fresh-install-only (Phase 8c guard): full/harden ship `enabled:true`, `--router-only` ships the **same block with `enabled:false`** (`jq '.sandbox.enabled = false'` — **not** stripped, so the floor stays pre-configured; flip `enabled:true` to turn it on and the statusline detects it). On an **existing** settings.json with no sandbox block, setup never rewrites the CC-owned file — the end-of-setup banner points at `linux/scripts/add-sandbox-block.sh` (idempotent `//=` add-if-missing merge; `--disabled` under router-only) so the user can opt in without losing their keys. (The `/sandbox` picker is **not** a reliable persistence path — it frequently no-ops + desyncs, anthropics/claude-code#47624 — and its toggle is invisible to the statusline (runtime-only, #30772); persisting `enabled` in user settings is the detectable mechanism.) The bwrap runtime is still installed in every mode (Phase 2). **Security note**: credential protection does **not** depend on the sandbox — the managed `permissions.deny[]` `Read(...)` rules (root-enforced, non-removable) cover the credential paths regardless. The sandbox `filesystem` floor is user-editable defense-in-depth that only applies while the sandbox is on; because the user can now disable the sandbox entirely, it is a strong **default** but not an **enforced** boundary. **Linux glob caveat**: the six leading-`**/` `Read(...)` globs in the managed `permissions.deny[]` (`**/.env`, `**/.env.*`, `**/*.pem`, `**/*.key`, `**/id_rsa`, `**/id_ed25519`) trigger a Linux startup warning ("Glob patterns in sandbox permission rules are not fully supported") because bubblewrap can't expand a wildcard-directory prefix into a fixed path to mask — fixed-prefix globs (`~/.ssh/**`) and the literal `filesystem.denyRead` paths translate fine and aren't flagged. It is **not** a misconfiguration: the **permission layer still enforces these globs** (Claude's Read/Edit tool + the bash readers it recognises — `cat`/`head`/`tail`/`sed`), so credential protection holds; only bubblewrap's FS layer drops them. Residual gap = an arbitrary subprocess *inside* the sandbox (`python`, `node -e`, a script opening the file itself) reading a project-relative `.env`/`*.pem`/`*.key`, mitigated by the literal credential-dir `denyRead` floor + the `network.allowedDomains`/managed `curl`/`wget`/`nc` denies that throttle exfiltration. Known won't-fix (anthropics/claude-code#32226, #56698); no suppression flag. The globs are **kept deliberately** — deleting them is the only way to silence the warning and would strip the load-bearing permission-layer protection (same principle as `feedback-explicit-deny-rules`). See *Troubleshooting* for the user-facing note.
- **Action-aware permission layer (`nah`)**: Phase 8e installs the `nah` Claude Code plugin (`manuelschipper/nah`, unpinned) as an additive PreToolUse guard. Stacks alongside `claude-managed-settings.json` denies. Per Anthropic's docs (code.claude.com/docs/en/permissions, hooks-reference), the evaluation order is: **PreToolUse hooks fire first**, then permission rules in order `deny → ask → allow`. A hook returning `"deny"` (or exit 2) blocks and **also overrides `allow[]`** rules; a hook returning `"allow"` cannot override `deny[]` or `ask[]` — those still fire. So both layers act as independent gates: the regex denies catch everything that matches their glob shape, and `nah` catches wrapper-evasion cases the regexes miss (`bash -c`, `python -c`, `xargs rm`, `find -delete`, `git push -f` short form, sudo-wrapped commands; content-scan: inline `python3 -c`/`node -e` code). nah's defaults (`src/nah/data/policies.json`) are looser than this repo's blanket denies on `pip install`, `curl *`, `git push --force*` — and since a hook `"allow"` cannot override `deny[]`, the regex denies remain load-bearing. Do **not** remove them in favor of nah (auto-memory entry `feedback-explicit-deny-rules` formalises the same principle). The repo also keeps its own `pretooluse-bash-guard.sh` exit-2 hook (deployed via managed-settings, root-enforced) alongside nah — one merged script carrying both the rm and the push check, so every Bash tool call pays a single bash+jq spawn, and a raw-substring fast path exits before even the jq fork when the input contains neither `rm` nor `push`. Not redundant with nah: under `--dangerously-skip-permissions` the `permissions.deny[]` rm rules are skipped and nah's `filesystem_delete: context` likely allows non-sensitive deletes, so the repo-owned exit-2 rm check adds a narrow deterministic floor there: it hard-blocks **direct** recursive-force `rm` (`rm -rf`/`-Rf`/`--recursive --force` — long options matched as anchored `--r`/`--f` prefixes, so the GNU getopt_long abbreviations `--recu --forc`/`--r --f` count too — any flag order/case, incl. subshell/command-substitution positions like `(rm -rf …)`/`$(rm -rf …)`, the quoting/escaping spellings `\rm`/`"rm"`/`r\m`/`rm "-rf"`, and the path forms `/bin/rm`/`./rm` — command word and flags are matched with shell quoting stripped and the command word reduced to its basename; matching is scoped per command segment, so flags belonging to a *different* command in the same line no longer false-positive). It does **not** catch argument-wrapped forms (`sudo rm -rf`, `bash -c '… rm -rf'`, `xargs rm`, `find -delete`) — those rely on nah's action/content scan (whose `filesystem_delete: context` may still allow non-sensitive deletes) and ultimately the bubblewrap sandbox. It is also a fallback if nah is uninstalled/disabled/regresses. The push check matches `main`/`master` only as whole push targets (bare branch, the `heads/…` dwim shorthand git resolves against `refs/heads/`, the full `refs/heads/…` path, or any of those as a refspec destination — branch names like `feature/domain-fix` no longer substring-match; tokens are compared with quotes/backslashes stripped and a leading `+` removed, so the force-refspec forms `+main`/`+refs/heads/master` and spellings like `"git" push`/`ma\in` block too) and also resolves the current branch (from the hook JSON's `cwd`, honouring a `-C` value) to block a bare `git push` — or an explicit `HEAD` refspec — while on main/master; outside a git repo that resolution fails open, and a path-invoked `/usr/bin/git push` isn't matched (accepted residual — plain `git` is what Claude runs; nah covers the path form). Known caveats: (1) **Under `--dangerously-skip-permissions` / `bypassPermissions`**: PreToolUse hooks still fire per Anthropic docs and community confirmation — the bypass flag skips the prompt + the deny/ask/allow rule chain, but hooks run *before* the prompt and remain active. So nah's `"deny"` / exit-2 decisions still block tool calls in this mode, making nah the **only** active policy layer (the `permissions.deny[]` regex rules are bypassed too). Hook `"ask"` decisions likely fall through to allow since prompts are off; only hook `"deny"` actually blocks. Known interaction bugs to watch: anthropics/claude-code#37745 (bypass can reset mid-session when hooks are configured), #47810 (both layers stop firing after background tasks complete), #40241 (subagents spawned via the Agent tool don't inherit bypass — nah hooks may not run there). Claude Code refuses to start under `--dangerously-skip-permissions` when running as root/sudo on Linux/macOS — a hard constraint. Only the bubblewrap sandbox (`sandbox.enabled`) is a kernel-level boundary that survives subagent escapes and hook regressions — but note it now lives in **user** settings (see *Sandbox control*) and is ON by default yet user-disableable via `/sandbox`, so it is no longer an *enforced* boundary; treat the managed `permissions.deny[]` + the exit-2 hooks as the load-bearing layer; (2) plugin form has no `.nah.yaml` tuning, only upstream defaults; (3) marketplace ref uses the `@claude-marketplace` branch (where upstream's `marketplace.json` lives — the default branch doesn't have it) and is otherwise unpinned; resolves on first `setup.sh` run only (re-runs skip on "already added"), so a hostile upstream update lands on fresh installs only — switch to `anthropics/claude-plugins-community` once `nah` lands there (Anthropic owns commit-SHA pin); (4) user-uninstall via `claude plugin uninstall nah --scope user` is re-installed (and re-enabled) on next `setup.sh`; but a user-**disable** via `claude plugin disable nah --scope user` is now **respected** — Phase 8e leaves an installed-but-disabled plugin disabled (install enables by default + the absent branch re-asserts enable, so a disabled state can only be a deliberate opt-out). To opt out: `disable` it (survives re-runs), or `uninstall` it and comment Phase 8e out to prevent reinstall.

## Troubleshooting

If LiteLLM fails to start, the service runs at `LITELLM_LOG=ERROR` which hides Prisma's "Run `prisma migrate resolve …`" recovery hints. To see them, edit `~/.config/systemd/user/litellm.service`, change `LITELLM_LOG=ERROR` to `LITELLM_LOG=INFO`, `systemctl --user daemon-reload && systemctl --user restart litellm`, and read `journalctl --user -u litellm -n 200`. Revert when done — INFO is very chatty in steady state.

**Statusbar shows `statusline skipped · restart to fix` and no trust prompt appears.** Caused by `IS_DEMO=1` leaking into the shell — Claude Code treats it as a "demo session" marker that silently suppresses the workspace-trust dialog without granting trust, so `statusLine` + hooks stay gated off and a restart doesn't help (anthropics/claude-code#37780, same flaw pattern as the fixed #10409). Phase 5a now strips it via `remove_profile_export "IS_DEMO"` (deletes the export from `~/.profile` and `unset`s it from the current shell). On a machine that ran an older setup, also check anywhere else it might be exported (`~/.bashrc`, `~/.zshrc`, container entrypoints, dotfiles), then relaunch `claude` and accept the trust prompt. As defense-in-depth Phase 8c only deploys `~/.claude/settings.json` on a fresh install — once Claude Code owns the file, re-running setup leaves it alone.

**Startup warning: "Glob patterns in sandbox permission rules are not fully supported on Linux."** Expected, and harmless to enforcement — not a misconfiguration. The six leading-`**/` `Read(...)` rules in `claude-managed-settings.json` (`**/.env`, `**/.env.*`, `**/*.pem`, `**/*.key`, `**/id_rsa`, `**/id_ed25519`) still block Claude's Read/Edit tool at the permission layer; only bubblewrap's filesystem layer can't apply them on Linux (no fixed path to mask). The residual gap — an arbitrary subprocess inside the sandbox reading a project-relative secret — is covered by the literal credential-dir `denyRead` floor plus the network-egress denies. There is **no flag to silence** the warning; removing the globs is the only way and would weaken the load-bearing protection, so we keep them (see *Sandbox control*). Refs: anthropics/claude-code#32226, #56698.

**No thinking blocks in Claude Code (Ctrl+O empty) while reasoning tokens are clearly billed.** The Anthropic→Responses adapter only surfaces thinking from **reasoning summaries**; `litellm_settings.reasoning_auto_summary: true` in `litellm-config.yaml` is what requests them (`summary: "detailed"`). Without it (LiteLLM's default), Azure returns reasoning items with an empty summary array and the translator emits zero thinking blocks — invisible by design, not a model problem. The key is undocumented in LiteLLM's config-settings docs but source-verified: `litellm_settings` keys are `setattr()` onto the `litellm` module, read by `is_reasoning_auto_summary_enabled()` (`llms/anthropic/experimental_pass_through/utils.py`) — present from `v1.84.0` (this repo's floor) through current main. Two expected behaviors even with it on: Azure does **not** generate a summary for every request (per its reasoning-models doc — some turns legitimately show no thinking), and a subscription without reasoning-summary access 400s with an error naming `summary` — in that case set `reasoning_auto_summary: false` in the **repo's** `linux/configs/litellm-config.yaml`, not the deployed copy: Phase 7 regenerates `~/.config/litellm/config.yaml` from the template on every run, so a hand-edit there is reverted on the next `setup.sh`.

**`OpenAIException - Cannot connect to host <resource>.services.ai.azure.com:443 ssl:<ssl.SSLContext …> [[SSL: TLSV1_UNRECOGNIZED_NAME] tlsv1 unrecognized name]`.** RFC 6066 alert 112 — something in the path read the SNI and rejected it — surfaced to Claude Code as a 500 that burns its whole retry budget. **Read the bracket before diagnosing:** `ClientConnectorError`, `ClientConnectorDNSError` and `ClientConnectorSSLError` all stringify as `Cannot connect to host …`, so the prefix alone does not distinguish a TLS alert from DNS or a refused connection. Not a config error — a wrong `api_base`/prefix/`api_version` fails on request #1, not after an hour of billed traffic; and the endpoint's cert is a `*.services.ai.azure.com` **wildcard**, so no per-tenant SNI binding can be missing. Observed once (2026-08-19, a Kali box, 22 consecutive failures over 8.5 min) and the **cause was never confirmed** — three candidates survived, so read the mitigations below as hardening, not as a diagnosis. (a) **PQC-inflated ClientHello.** OpenSSL 3.5+ defaults to the hybrid `X25519MLKEM768`, whose 1216-byte key share takes LiteLLM's ClientHello to ~1548B — past a 1460B MSS, so it splits across TCP segments and an SNI-inspecting middlebox reading only the first one loses the hostname. Documented across HAProxy, Traefik, F5 and AWS Network Firewall (the "tldr.fail" class); responses vary by device — RST, silent drop, wrong default cert, or alert 112. (b) **An ambient egress proxy.** `aiohttp_transport.py::_get_proxy_settings` consults `urllib.request.getproxies()` unless `DISABLE_AIOHTTP_TRUST_ENV=True` (memoized per host in `self.proxy_cache`, so once per host rather than per request — the concern is interception, not CPU), and a `--user` unit inherits the whole user-manager environment (`systemd.exec`), so a desktop proxy setting tunnels provider traffic through a TLS terminator that may rebuild the handshake with a bad SNI. It cannot arrive via `~/.config/litellm/env` — `collect_litellm_provider_vars` matches only `*_API_KEY|_API_BASE|_API_VERSION|_API_TOKEN` plus a named list. (c) **An Azure-side front-end incident** — no evidence either way; the discriminator below is what isolates it. *Separately* ruled out and not worth re-chasing: uvloop (its `sslproto` buffers through a MemoryBIO exactly as asyncio's does — the `uvloop/sslproto.pyx` frames are only where the exception surfaces) and aiohttp dropping SNI (it sets `server_hostname` from the request host on both the direct and proxy paths). Discriminate in one minute: `openssl s_client -connect $H:443 -servername $H -brief </dev/null` versus the same with `-groups prime256v1`, plus `systemctl --user show-environment | grep -i proxy`. First fails + second succeeds → (a); a proxy var appears → (b), and fix it at its source too, since this repo's mitigation only stops *LiteLLM* using it; both fail with no proxy var → (c) or the local network, and nothing here is the fix. `litellm.service` + `litellm-docker-compose.yml` carry **two** `Environment=` mitigations for (a) and (b) — `SSL_ECDH_CURVE` and `DISABLE_AIOHTTP_TRUST_ENV` — plus `AIOHTTP_TTL_DNS_CACHE=10`, which addresses neither and narrows (c): these endpoints publish a ~10s A record behind two Traffic Manager layers, LiteLLM overrides aiohttp's matching 10s default to 300s (`constants.py`), and aiohttp never invalidates a cached address on connect failure — so a withdrawn front end stays pinned for up to five minutes. **All three must be env vars, not `litellm_settings` keys** (which would otherwise work — `proxy_server.py` `setattr`s them onto the module, the `reasoning_auto_summary` precedent): the cost-map and beta-header fetches run at module level during `import litellm`, *before* config.yaml is parsed, so a config-file pin would silently miss the very host the single-curve constraint had to accommodate. **The curve is `prime256v1`, not the `X25519` LiteLLM's own source comment recommends**: X25519 makes the Azure endpoint reset outright (6/6), and `set_ecdh_curve` takes exactly **one** curve (a colon-separated list raises `ValueError`), so it must satisfy every host the daemon dials — the provider endpoint plus `raw.githubusercontent.com` (cost map + beta-headers config, `litellm/__init__.py`). `secp384r1` also reaches Azure but fails against `api.github.com`, npm and osv.dev; `prime256v1` was the only value that passed everywhere, and it is mandatory-to-implement in TLS 1.3. Note that constraint set is partly self-imposed and can grow silently: `raw.githubusercontent.com` is only in it because `LITELLM_LOCAL_MODEL_COST_MAP` is deliberately left unset (see *Telemetry*), and **any future outbound integration — a guardrail, a secret manager, a callback — joins it with no signal**. Re-check the curve against a new host before adding one. Rejected alternative: a scoped `OPENSSL_CONF` keeps five groups instead of one, but overriding `[openssl_init]` after a `.include` silently discards the distro's `MinProtocol`/`CipherString` (measured: 144 → 60 ciphers) and couples the unit to per-distro section names.

**Proxy never serves, `litellm` burns CPU, and any `prisma` command hangs with no output — including read-only `prisma migrate status`.** The Prisma CLI is a Node program; its first invocation installs a private Node runtime under `~/.cache/prisma-python/nodeenv` (minutes on a cold or slow link). prisma-client-py's `ensure_cached()` decides whether to install by testing that directory for **existence alone**, so a bootstrap killed part-way leaves a directory with no `bin/node` that is then skipped forever — every later invocation hangs. **The terminal state is a hang, not a crash loop, and systemd reports it healthy**: `proxy_cli.py` runs a bare `subprocess.run(["prisma"], capture_output=True)` — unconditional whenever `DATABASE_URL` is set, no timeout, *before* any migration branch — so under `Type=simple` the unit sits `active (running)`, uvicorn never binds, and nothing ever exits for `StartLimitBurst` to count. Do not reach for `TimeoutStartSec` (inert for `Type=simple`) or restart backoff (it lengthens the cycle, moving a slow loop further outside the give-up envelope). The restart loop you may also see in the journal is a *different*, earlier and bounded phase — see the `ModuleNotFoundError` fingerprint below. Two things killed the bootstrap here, both fixed in Phase 4a: `uv tool install --upgrade` rebuilt the venv while the unit was live, so it restarted into a half-built venv (`ModuleNotFoundError: No module named 'litellm'` — the fingerprint of that window) and then raced this script over the same toolchain cache — **and the first cut of the fix missed the very boxes it targeted**: the stop was gated on `systemctl is-active`, which is non-zero for `activating (auto-restart)` (~10s of every ~11s crash-loop cycle) and for `failed` (start-limit parked), so on an already-wedged box the gate read "not active", skipped the stop, and `Restart=always` kept firing into the rebuild (observed 2026-08-19). The stop is now **unconditional** (free no-op on an inactive unit, cancels any queued auto-restart) with restore keyed on the unit *file*, and the window is additionally held shut by `systemctl --user mask --runtime` — nothing, operator included, can start the unit mid-rebuild; `--runtime` keeps the mask in `/run` so a hard-killed run is healed by reboot, and an EXIT trap unmasks + restores on every abort path. The regenerate gate is an **import probe** (`from prisma import Prisma` — the exact import the proxy performs at startup), not a file-existence glob: a generate interrupted by the pre-mask race leaves a `client.py` that exists but cannot import, which an existence check then skips forever. Diagnostic caveat: **`NRestarts` is not a crash-loop signal on these boxes** — `restart_user_service_if_stale` runs `reset-failed` before every restart, which zeroes the counter; count `Started` lines in the journal instead; and litellm ≤1.96.2 pins `litellm-proxy-extras==0.4.81`, which shares one 60s `subprocess.run` timeout between the bootstrap and each migration command, so a slow bootstrap is indistinguishable from a slow migration and dies at 60s. Upstream fixed the second half in 0.4.84 (`prisma_toolchain.py::heal_incomplete_nodeenv_cache` + a separate 600s budget), pinned by litellm ≥1.97.0; Phase 4a heals both caches itself regardless — 0.4.84's heal only guards `setup_database`, and the heals must run even when `prisma generate` is gated off (no-version-change runs), which is why the warm-up `prisma --version` is unconditional. **There are two prisma cache trees, and hand-run recovery touches the wrong one by default**: `ensure_cached()` runs on *every* prisma invocation and npm-installs the CLI into `binary_cache_dir` — prisma-client-py's default is **versioned** (`~/.cache/prisma-python/binaries/5.17.0/<engine>/`), but the unit and setup.sh pin the **flat** `~/.cache/prisma-python/binaries` via `PRISMA_BINARY_CACHE_DIR`. A `prisma --version` in an interactive shell (where that var is unset) warms the versioned tree; the service keeps reading the flat one and re-runs `npm install` untimed at every start — the fingerprint is a **lone argument-less `prisma` process burning CPU** under the unit, repeatedly killed mid-install by restarts (SIGKILL skips the wrapper's entrypoint-unlink cleanup, so `node_modules` is left half-populated and the loop sustains itself). A related but distinct grind — the main litellm process at >100% CPU logging `Running prisma migrate deploy` — is the migrate-posture reconciliation storm; that one is retired by `--use_prisma_db_push` (see *DB schema posture* under Key Conventions). **Recovery: run the updater** — Phase 4a's heal + warm-up does all of this, bounded and supervised. Manual fallback for when the updater itself is unusable (`prisma` is *not* on the interactive PATH — `uv tool install` links console scripts only for the primary package, so it lives at `~/.local/share/uv/tools/litellm/bin/prisma`): `systemctl --user stop litellm` (kills any grinding child in the same cgroup), then `export PATH="$HOME/.local/share/uv/tools/litellm/bin:$PATH"; set -a; . ~/.config/litellm/prisma.env; set +a` — **load-bearing, not hygiene**: prisma.env is the unit's own switch set (flat cache dir, global-node opt-out, …), and `PRISMA_BINARY_CACHE_DIR` is read from it below — then `rm -rf ~/.cache/prisma-python/nodeenv "$PRISMA_BINARY_CACHE_DIR/node_modules" "$PRISMA_BINARY_CACHE_DIR/package.json" "$PRISMA_BINARY_CACHE_DIR/package-lock.json"` (npm-owned entries only — the engine copies inside `node_modules/@prisma/engines/` go with it, and the CLI restores them from `~/.cache/prisma/master/<hash>/` without network), then `prisma --version </dev/null` and let it finish, then start the unit. If `prisma --version` stalls again with no output, read the process tree before blaming the network: a `~/.bun/bin/node --version` child is the bun-REPL stall (next entry); a `node …/npm-cli.js install` or an engine download is the box's egress path (Node/npm/`binaries.prisma.sh`) — `--version` needs `binaries.prisma.sh` only when the computed target's engine is missing from both caches. GNU `timeout` signals the whole process group, so a timed-out step leaves no orphaned npm/node behind.

**`prisma --version` / `prisma generate` stall for the whole 600s budget with a `~/.bun/bin/node --version` child in the process tree** (observed 2026-08-22 on a Kali overlay box: warm-up timed out → caches wiped → generate timed out → LiteLLM down; network to `binaries.prisma.sh`/`registry.npmjs.org`/`nodejs.org` was fine, npm's log ended `info ok`). prisma-client-py resolves a Node binary before *every* CLI call and, with `PRISMA_USE_GLOBAL_NODE` at its default `true`, first probes `shutil.which('node') --version` with `stdout=PIPE` and **stdin inherited** (`prisma/cli/_node.py::_get_binary_version`). `which node` on these boxes is the Phase 3 `~/.bun/bin/node → bun` symlink (`~/.bun/bin` leads the overlays' `DEPLOY_BIN_PATH` and sits in `USER_TOOL_PATH`/`LITELLM_PATH`). Through bun 1.3.x that wrapper printed `error: Missing script to execute … does not support a repl` and exited 1 → the library fell through to its private nodeenv → worked; **bun 1.4.0** (pulled in by Phase 3's every-run `bun upgrade`) added a Node-compatible REPL, so `node --version` with a TTY on stdin prints `Welcome to Bun v1.4.0 (Node.js-compatible REPL …)` and waits for input forever (with stdin at `/dev/null` it still errors instantly — the reason the stall is invisible under the systemd unit and in non-interactive reproductions, and visible in an interactive `update-ct-*` run). Fingerprint: `ps -eo pid,ppid,stat,etimes,args --forest` shows `python …/bin/prisma <cmd>` → `…/.bun/bin/node --version` sleeping for minutes, no npm, no CPU. Fix (all in place): `PRISMA_USE_GLOBAL_NODE=false` in `~/.config/litellm/prisma.env` (sourced by `run_prisma`, `EnvironmentFile=` in the unit), plus `</dev/null` on the wrapper — the private nodeenv is the only toolchain consulted. Not applied to the docker compose file: the image relies on its own `/usr/bin/node` by design. If a hand-run `prisma` stalls the same way, you ran it without sourcing prisma.env. Version probe to reproduce anywhere: `script -qfc "timeout 15 ~/.bun/bin/node --version" /dev/null` (REPL banner = affected bun).

**A `prisma db push --accept-data-loss --skip-generate` process in the process list.** Expected, at **every** service start — that is the db-push posture (see *DB schema posture* under Key Conventions) doing its startup schema sync, not a regression; on a box recovering from the pre-fix wedge the full arc is high-CPU litellm (old grind) → a lone bare `prisma` (bootstrap probe reinstalling the CLI) → `db push` (the new posture's normal step). Bounds, verified in 1.96.2 source (`prisma_client.py::PrismaManager.setup_database`): `subprocess.run(..., timeout=60, check=True)`, ≤4 attempts per start with 5–15s sleeps, then the proxy **continues startup either way** — a failed sync cannot crash-loop the unit. Engines are not downloaded inside that budget: the Phase 4a warm-up's `prisma --version` makes the CLI fetch the computed target's query **and schema** engines (hash = prisma-client-py 0.15.0's `expected_engine_version`) into `~/.cache/prisma/master/<hash>/` and `node_modules/@prisma/engines/` — npm's `@prisma/engines` postinstall would do the same but is disabled by the overlays' `ignore-scripts=true` — so the in-service `db push` finds them warm. How to read an observation: a **single PID** older than ~70s is impossible (SIGKILL at 60s) — check `ps -o etimes= -p <pid>`; **successive PIDs over minutes** mean the attempts are failing (prisma's own stdout/stderr are uncaptured and land in the journal) or the unit is restarting between starts (count `Started` lines — `NRestarts` is zeroed, see above). Two caveats: litellm's per-attempt retry messages are `verbose_proxy_logger.warning` and therefore **invisible at `LITELLM_LOG=ERROR`** (the "Database migration failed but continuing startup" line is a `print` and does show); and on timeout the SIGKILL hits only the Python wrapper — its Node/schema-engine **grandchild survives** in the unit's cgroup and can hold Prisma's Postgres advisory lock, timing out the following attempts until it finishes on its own or the next unit stop/restart kills the cgroup (upstream behaviour, self-limiting, not repo-fixable). Quick health read: `curl -sf 127.0.0.1:4000/health/liveliness` — if it answers, the start completed and the sync either succeeded or was skipped past. `wait_for_litellm` (common.sh) accounts for this: Phase 7 grants the long budget (`LITELLM_WAIT_LONG`, 900s, progress note at 60s) only when the unit was actually started this run (`restart_user_service_if_stale` reported a start — in native mode every run, since Phase 4a always defers the single start to Phase 7) — so a long first sync no longer draws a false "not responding" warning, while an untouched running service keeps the 90s default. The 15-minute ceiling exists for CPU-starved VMs where every arc step stretches (observed 2026-08-20: a converging start outlived the old 360s budget, and the resulting warning invited an overlay recovery restart that killed it mid-arc); it is safe to grant because the wait bails out early — immediately when the unit parks `failed` (start-limit), and as soon as `NRestarts` grows ≥3 during the wait (crash-loop; the counter was zeroed by `reset-failed` before the initial restart, so any growth is loop) — so a genuinely broken box exits the wait in seconds-to-a-minute, never sits out 15 minutes. Silence past the granted budget with the unit still `activating`/`active` is a real failure.

**An upgrade run takes tens of minutes, with successive single-CPU processes.** Before diagnosing, know what the mechanism itself costs — measured on litellm 1.96.2, everything pinned to **one** CPU core, cold caches: toolchain warm-up ≈ 11s, `prisma generate` ≈ 13s, import probe ≈ 9s, `prisma db push` ≈ 6s per spawn (the actual sync inside it is **186ms** on an empty *or* converged DB — 68 tables; DB size is irrelevant to a slow run), bare `prisma` spawn ≈ 5s, `import litellm.proxy.proxy_server` ≈ 17s cold (first start after a venv rebuild pays the `.pyc` compile) / ≈ 10s warm. Whole Phase 4a arc ≈ 50s wall on an unconstrained box, ≈ 90s of single-core CPU total; hard bounds: 600s warm-up + 600s generate + 4×60s db push per start. Anything beyond that is **downloads and disk I/O**, not the mechanism: uv venv delta, node tarball (~50MB, extracts to ~440MB), npm prisma (~25MB), engines (computed target ~45MB fetched by the CLI during the warm-up + ~75MB of foreign-`binaryTargets` query engines at first generate — once per engine hash, see the Phase 4a row), `claude update` (~300MB), plus the ~2GB venv rebuild — network/disk-bound and worst on small VMs, where each step also visibly pegs its single core (xz, gunzip+sha256, `.pyc` compile). To attribute a specific slow run: every `log` line is timestamped and the warm-up/generate steps print durations, so read the gaps in the scrollback or journal — a step that ran long but *finished* inside its budget was the bound doing its job, not a wedge (the wedge fingerprint is the hang entry above). One multiplier is fixed, not just bounded: the start arc used to be **paid up to three times per upgrade run** — Phase 4a's restore started the new binary, Phase 7's restart (always fired on upgrade runs) cgroup-killed that still-converging start and re-ran the arc, and an overlay's end-of-run recovery could kill the second one too (observed 2026-08-20 on a CPU-starved VM: the litellm parent + bare `prisma` + `db push` trio cycling for ~15 min, partly against a Postgres that a restored snapshot had left down and Phase 6 hadn't started yet at 4a-restore time). Phase 4a now never starts the unit itself — every native run defers the single start to Phase 7, sequenced after the `pg_isready` gate and against the freshly deployed unit (a 4a start was also killed by Phase 7's restart on any env/config/unit change, e.g. every box's first run after a template edit).

**The same churn at every reboot.** Same mechanism, different trigger: a `--user` unit cannot `After=` the system `postgresql@` instance, so at boot litellm raced Postgres and each losing cycle cost the full arc — import (~10–17s) + bare `prisma` (~5s) + failed `db push` retries (~30–60s) + startup connect (3 tries) → the startup event raises (`allow_requests_on_db_unavailable` unset → `handle_db_exception` re-raises, verified 1.96.2 `db/exception_handler.py`) → exit → `Restart=always` — and the 20/600s start-limit deliberately never trips (cycle > 30s envelope), so it loops until Postgres answers. Fixed by the units' `ExecStartPre` pg_isready gate (see *Postgres readiness gate* under Key Conventions): waiting now costs 5ms probes and the arc runs once. `allow_requests_on_db_unavailable` was considered and rejected — it changes auth semantics for a problem the gate solves; mid-run DB outages are already handled by litellm's reconnect watchdog.
